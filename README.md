# korylus-tools

> 日本語 | [English](./README.en.md)

Korylusプロジェクトで共通利用する開発ツールを集約したリポジトリです。
GoのツールはGoのモジュール (`cmd/`・`internal/`) に、RustのツールはCargoのワークスペース (`crates/`) に置いています。

## koryluslint

`koryluslint` はKorylus共通のリンタをまとめた単一バイナリです。
サブコマンドで各リンタを呼び分けます。

| サブコマンド | 役割                                                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------------------- |
| `comment`    | ソースコードの日本語テキストスタイル (korylus-lang.md §3) を検査する                                          |
| `md`         | Markdownドキュメントの句点改行 (semantic line break) と日本語テキストスタイル (korylus-lang.md §3) を検査する |

### 使い方

```sh
koryluslint comment [-base=<ref>] [paths...]
koryluslint md [-base=<ref>] [--all] [--write] [paths...]
```

`-base=<ref>` を渡すと、`<ref>` 以降に追加された行だけを検査します (差分スコープ)。

`comment` が見る範囲は形式ごとに違います。

| 形式                      | 検査対象                                                                          |
| ------------------------- | --------------------------------------------------------------------------------- |
| `.go`                     | コメント                                                                          |
| `.templ`                  | 行頭 `//` のコメント                                                              |
| `.sh`                     | Bashの構文解析で抽出したコメント・引数などの文字列・ヒアドキュメントの本文        |
| `.ts`                     | TypeScriptの構文解析で抽出したコメント・文字列の本文 (テンプレートリテラルを含む) |
| `.rs`                     | Rustの構文解析で抽出したコメント・docコメント                                     |
| `.sql` / `.css` / `.toml` | 日本語を含む行                                                                    |

コメント以外の日本語も検査するのは、i18nの訳文やシェルが出力するメッセージも§3の対象だからです。
シェルのコマンド名・オプション・展開式や、TypeScriptの補間式の演算子などは本文に含めません。
引用符で囲まないシェルの引数どうしの区切りは、出力される文面のスペースとして検査します。
`.sh` / `.ts` では、コメント内のMarkdownインラインコードは除外しますが、文字列内のバッククォートは本文として検査します。
`.sql` / `.css` / `.toml` は行全体をMarkdownとして扱うため、バッククォートで囲まれた範囲は文字列の中でも除外されます。
シェル・TypeScriptの構文解析に失敗したファイルは、標準エラー出力に通知してスキップします。

日本語を含まない行は検査しません。
生成物の除外は`_templ.go`と、先頭20行以内に`// Code generated ... DO NOT EDIT.`の定型ヘッダーを持つファイルが対象です。
それ以外の生成物や、SQL・CSS・TOMLのコード中に日本語がある場合は、行単位の検査に含まれます。

`.go` の文字列リテラルは検査しません。
描画結果と突き合わせるテストのリテラルは、テンプレートの出力に合わせて §3に反する形を意図して持つためです。
`.rs` の文字列リテラルも検査しません。
エラーメッセージがコマンド名やオプションをスペースで区切って含み、テストのデータが §3に反する形を意図して持つためです。
Rustのdocコメントのコード例 (コードフェンス・字下げしたコードブロック) は、rustdocのMarkdownとして識別して検査から外します。

`md` では、`--all` は差分行だけでなく全 `.md` ファイルを全行検査し、`--write` は句点改行をその場で修正します。
日本語テキストスタイルの違反は書き換え後の行番号で報告し、違反が残る場合は終了コード1を返します。

## korylusflow

`korylusflow` は、作業計画書のタスクを役割ごとの対話セッションで進めるときに、番と次の指示を決めて状態を記録するCLIです。
実装者・レビュアー (Codex)・レビュアー (Claude Code) のセッションは、それぞれ自分の番を `korylusflow` に尋ね、返ってきた指示どおりに作業してから完了を記録します。
次に何をするかは `korylusflow` が決め、エージェントには決めさせません。
`korylusflow` 自身はClaude Code / Codexを起動しません。

### 使い方

```sh
korylusflow wait <計画書> -role=<役割> [-timeout=<時間>]
korylusflow done <計画書> -role=<役割>
korylusflow status <計画書>
korylusflow report <計画書>
```

どのサブコマンドもプロジェクトのルートで実行します。
計画書は、WikinoのページのURL (`https://wikino.app/s/<スペース>/pages/<ページ番号>`) で指定します。
パスやページ番号だけの指定は受け付けません (「[計画書名とWikinoのページの計画書](#計画書名とwikinoのページの計画書)」)。
役割は `implementer` (実装者)・`reviewer-codex` (レビュアー (Codex))・`reviewer-claude` (レビュアー (Claude Code)) のいずれかです。

| サブコマンド | 役割                                                                                                                                                                                        |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `wait`       | 役割の番が来るまで待ち、次の指示を標準出力に書く。`-timeout` を過ぎても番が来なければ `action: wait` を返す                                                                                 |
| `done`       | 進めているステップの完了を確かめて記録し、次のステップを決める。実装のステップでは動作確認の項目を、作業報告書のステップではURLと処理の流れを書かなかった理由を、標準入力からJSONで受け取る |
| `status`     | 計画書の進行状況と、現在のタスク・ステップ・番の役割・人を待っている理由・所要時間を表示する                                                                                                |
| `report`     | マージするPRなど、状態・計画書・gitから集めた事実を標準出力に書く。状態は書き換えない                                                                                                       |

指示の先頭行は `action: <種類>` (`implement`・`work`・`review`・`fix`・`ask`・`report`・`finish`・`wait`) です。
続けて、実行するスキルと引数、終わったあとの手順を毎回すべて書きます。
コンテキストが圧縮されたあとでも、直近の指示だけで続けられるようにするためです。

`done` の終了コードは次のとおりです。

| 終了コード | 意味                                                                        |
| ---------- | --------------------------------------------------------------------------- |
| 0          | 完了を記録した                                                              |
| 1          | エラー                                                                      |
| 2          | 完了の条件を満たさず、記録を受け付けなかった (理由を読んで直せばやり直せる) |

### 計画書名とWikinoのページの計画書

計画書名は、状態の置き場所・ブランチ名・`korylusflow report` の見出しに使う名前です。
計画書の最初の `## ` の見出しより前に、次の形の行で書きます。
値には英小文字・数字と、間に挟むハイフンだけを使います。

```markdown
**計画書名**: feature-name
```

この行は必須です。
ループの途中で計画書名を変えると、状態の置き場所が変わって続きから進められなくなります。

Wikinoのページの計画書は、[Wikino CLI](https://github.com/wikinoapp/wikino/tree/main/cli) の `wikino` コマンドで、下書きがあれば下書きを、無ければページを読みます。
実装者が付けたチェックや実装判断ログは、公開するまで下書きにしか無いためです。
`korylusflow` はWikinoに書き込まないため、`wikino auth login <スペース>` でログインするトークンには読み取りの権限があれば足ります。
`korylusflow` は `https://wikino.app` のページを読むため、既定の接続先を変えている環境では `--host=https://wikino.app` を付けてログインします。
未ログインやレート制限で読めなかったときは、状態を書き換えずにエラーで終わります。

### ベースブランチ

別の計画書のマージ前のブランチの上に積むときは、計画書の最初の `## ` の見出しより前に、リポジトリの最初のタスクのブランチを作る元のブランチを書きます。
値は `<ディレクトリのパス>=<ブランチ名>` を `, ` で区切って並べます。
パスはタスクの接頭辞と同じく、リポジトリの中のディレクトリの絶対パスで、そのディレクトリを含むリポジトリのベースになります。

```markdown
**ベースブランチ**: /workspace=prev-feature-1-3, /korylus-tools=prev-feature-1-2
```

タスクのブランチを作る元のブランチは、次の順で決めます。
作業ツリーの現在のブランチは使いません。

1. 同じリポジトリの前のタスクのブランチがローカルにあれば、そのブランチ
2. ベースブランチの行にそのリポジトリのブランチがあれば、そのブランチ
3. どちらも無ければ、develop、無ければmain

行のパスからリポジトリを求められないとき・同じリポジトリに別々のブランチを書いたとき・行に書いたブランチがローカルに無いときは、自動で進めず、実装者に人へ尋ねるよう指示します。
行の書式の誤り (`=` が無い・パスが `/` で始まらない・ブランチ名が空・同じパスや行の重複) は、計画書を読み取れないエラーになります。
ブランチを準備し終えたタスクのベースは、あとから行を直しても変わりません。

### 1タスクの流れ

1. タスクの接頭辞からリポジトリを求め、ブランチ `<計画書名>-<タスク番号>` を作る。元のブランチは「[ベースブランチ](#ベースブランチ)」の順で決める
2. 実装者が `/korylus-do-plan-task` で実装し、コミットする
3. レビュアーが `/korylus-review` でレビューする。1回目はCodex、2回目以降は前回と別の役割が行う
4. `korylusflow` がレビュードキュメントの自動対応可の指摘に推奨の選択肢で回答し、レビュアーが修正してコミットする
5. Request Changesなら3へ戻り (上限3回)、Comment / Approveなら次のタスクへ進む

人が行うタスク・要人間判断の指摘・レビューの上限に当たったときは、そのときのセッションに人へ尋ねるよう指示します。

計画書の最後まで進むと、実装者へWikinoの作業報告書を書くよう指示します (`action: report`)。
指示には、リポジトリごとの最後のタスクのブランチとその先頭のコミット、前の回で書いた作業報告書のURLを書きます。
実装者は `/korylus-write-report` で作業報告書を書き、URL (`{"location":"<URL>"}`) を `done` に渡します。
処理の流れを書かなかったときは、理由を添えます (`{"location":"<URL>","walkthrough_skipped":"<理由>"}`)。
URLは `https://` で始まるものにします。
`korylusflow` はURLと理由を記録するだけで、作業報告書の本文は読まず、Wikinoにも書き込みません。

処理の流れを書いたときは、続けて作業報告書をレビューします。

1. レビュアーが `/korylus-review-doc <作業報告書のURL> prefix=<計画書名>-report` でレビューする。1回目はCodex、2回目以降は前回と別の役割が行う
2. `korylusflow` がレビュードキュメントの自動対応可の指摘に推奨の選択肢で回答し、レビュアーが作業報告書の下書きを修正する。下書きはコミットしないため、修正の完了ではブランチとコミットを確かめない
3. Request Changesなら1へ戻り (上限3回)、Comment / Approveなら作業報告書のレビューを終える

要人間判断の指摘と上限の扱いは、タスクのレビューと同じです。
レビュードキュメントは回をまたいで同じ接頭辞 (`<計画書名>-report`) の連番で書き、前の回のレビューの修正検証の対象にします。
処理の流れを書かなかったときは、コードと照合する処理が無いため、レビューを飛ばします。

タスクの接頭辞は次のとおりに読みます。

| 接頭辞                                  | 作業するディレクトリ                                         |
| --------------------------------------- | ------------------------------------------------------------ |
| `[/workspace/go]` など `/` で始まるもの | そのパス                                                     |
| `[Go]`・`[Rails]`・接頭辞無し           | `/workspace/go`・`/workspace/rails`・`/workspace` として読む |
| `[implementer]`                         | なし (実装者がブランチを作らずに行うタスク)                  |
| それ以外 (作業する人の名前)             | なし (人が行うタスク)                                        |

`[implementer]` のタスクは、Wikinoの下書きの作成や、ブランチを作らずに直接コミットしているリポジトリの編集のように、実装者が行えてブランチとPRを作らない作業に使います。
ブランチを準備せず、レビューも挟まずに、実装者へ作業を指示します (`action: work`)。
実装者はコミットせず、取り返しのつかない操作の前には人の了承を得て、結果を人に示します。
人が結果を確かめて計画書のタスクにチェックを付けたら、完了にします。

タスクの下に `**担当**:` の行があるときは、接頭辞をブランチを作るリポジトリのパスとしてだけ読み、担当を行の値から読みます。

```markdown
- [ ] **1-1**: [/workspace/go] マイグレーションを作る
- [ ] **1-2**: ヘルプページの下書きを作る
  - **担当**: implementer
- [ ] **1-3**: ヘルプページの下書きを公開する
  - **担当**: shimbaco
```

| 担当の行            | 接頭辞         | タスクの対象                                  |
| ------------------- | -------------- | --------------------------------------------- |
| 無し                | 上の表のとおり | 上の表のとおり                                |
| `implementer`       | パス           | 実装者がそのリポジトリでブランチを作るタスク  |
| `implementer`       | 無し           | 実装者がブランチを作らずに行うタスク          |
| それ以外 (人の名前) | パス・無し     | 人が行うタスク                                |
| 有り                | パス以外       | 人に尋ねる (接頭辞と担当の行が食い違っている) |

1つのタスクに担当の行が複数あるときと、値が空のときは、計画書を読み取れないエラーにします。
`korylusflow status` と `korylusflow report` では、担当の行があるタスクに担当を添えて示します (例: `1-2 ヘルプページの下書きを作る (担当: implementer)`)。

### 作業報告書と事実の表示

作業報告書は、実装者がWikinoのページに書く、処理の流れとフィードバックの節を持つドキュメントです。
人は作業報告書を読んでフィードバックを溜め、計画書にフィードバック対応のタスクを足してループを再び回します。
計画書の最後まで進むたびに、実装者が同じ作業報告書を更新し、`korylusflow` はその回のURLを記録します。

`korylusflow report` は、状態・所要時間の記録・計画書・gitから集めた事実を標準出力に書きます。
エージェントの説明を混ぜず、記録にある事実だけを並べます。
状態を書き換えないため、ループの途中でも実行できます。

- 概要 (計画書・計画書の開始・最新の回の作業報告書のURL・リポジトリごとにマージするPR)
- タスクごとの変更 (1タスク1行の表で、ブランチ・変更行数・想定行数・レビューの評価)
- 実装者がブランチを作らずに行ったタスク
- 先送りした指摘
- 保護領域 (宣言の内容と、差分を見るコマンド)

所要時間と人を待った時間は、`korylusflow status` で表示します。

`korylusflow` はpushとPRの作成・マージを行いません。
人が作業報告書を確かめてから、`korylusflow report` のマージするPRのとおりに、リポジトリごとに最後のタスクのブランチから最初のタスクの元のブランチへのPRを1つ作り、merge commitでマージします。
前のタスクのブランチが残っておらず、最初のベースから作り直したなどでブランチが1本に繋がっていないときは、繋がった並びごとにPRを示します。

「[ベースブランチ](#ベースブランチ)」の行で、既定のベース (develop、無ければmain) と違うブランチの上に積んだときは、そのベースが既定のベースに取り込み済みかをローカルのブランチで確かめて示します。

| ベースの状態               | ベースの列     | 添える説明                                                 |
| -------------------------- | -------------- | ---------------------------------------------------------- |
| 既定のベースに取り込み済み | 既定のベース   | 取り込み済みであること                                     |
| まだ取り込まれていない     | 積んだブランチ | 積んだブランチのPRを先にマージしてから、既定のベースへ出す |
| ローカルに無い             | 積んだブランチ | 取り込み済みかを確かめられないこと                         |

Markdownの作業報告書 (`report-<版>.md`) を作っていたときの状態も、そのまま読めます。
それまでの版はページを持たない回として引き継ぎ、次に計画書の最後まで進んだときに作業報告書のページを新しく作ってもらいます。
すでに作った `report-<版>.md` は消しません。

### 状態の置き場所

状態は、計画書と一緒に履歴として残すため `docs/private/plans/files/<計画書名>/` に置きます。

| ファイル         | 内容                                                 |
| ---------------- | ---------------------------------------------------- |
| `flow.json`      | 現在のタスク・ステップ・番の役割と、タスクごとの記録 |
| `flow.lock`      | ファイルロック用の空のファイル                       |
| `timeline.jsonl` | ステップごとの開始と終了の時刻                       |

### インストール

`make install-korylusflow` でビルドし、`~/.local/bin/korylusflow` に置きます (`BINDIR=<ディレクトリ>` で置き場所を変えられます)。
ループの途中でブランチを切り替えても実行中のコードが変わらないよう、作業ツリーから `go run` で実行せず、ビルドした実行ファイルを使います。

## korylusfactory

`korylusfactory` は、作業計画書を人が付き添わずに進めるためのCLIです (Rust)。
ロードマップで承認された作業計画書を1本ずつ選び、Claude CodeとCodexのセッションを無人で起動して、実装・レビュー・修正・作業報告書までを進めます。
人間の判断が要る場面ではその作業計画書を止め、人間キュー (Wikinoのページ) に項目を積んで知らせます。
人間が項目に回答を書いて公開するか、コマンドで再開するのを待ちます。

```sh
korylusfactory start
korylusfactory status [--json]
korylusfactory resume [--review-limit <回数>]
korylusfactory queue list [--all] [--json]
korylusfactory queue show <ページ番号> [--json]
korylusfactory queue answer <ページ番号> [<回答>...] [--json]
korylusfactory --version
```

どのサブコマンドも、プロジェクトのルートで実行します。

### 設定ファイル

プロジェクトのルートの `docs/private/factory/config.json` に、ロードマップのURLと、承認とみなす節・完了とみなす節を書きます。
人間キューと人間待ちの知らせを使うときは、プロジェクト名・人間キューの置き場・通知のコマンドも書きます。

```json
{
  "roadmap": "https://wikino.app/s/<スペース>/pages/<ページ番号>",
  "sections": ["やってる", "優先度: 高", "優先度: 中"],
  "done_sections": ["リリース待ち", "やった"],
  "project": "<プロジェクト名>",
  "queue": { "space": "<スペース>", "topic": 12 },
  "notify": { "command": ["<通知のコマンド>", "<引数>"] }
}
```

| 項目            | 内容                                                                                                                                             |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `roadmap`       | ロードマップのページのURL。`https://wikino.app` のページだけを受け付けます                                                                       |
| `sections`      | 承認とみなす節の見出し (H2)。書いた順に進めます。省略すると「やってる」「優先度: 高」「優先度: 中」の順になります                                |
| `done_sections` | 完了 (マージ済み) とみなす節の見出し (H2)。省略すると「リリース待ち」と「やった」になります                                                      |
| `project`       | プロジェクト名。英数字・ハイフン・アンダースコアで書きます。人間キューの項目と通知のコマンドに渡します。`queue` か `notify` を書くときは必須です |
| `queue`         | 人間キューの置き場 (`space`: スペースの識別子、`topic`: トピックの番号)。省略すると項目を積まず、`resume` だけで再開します                       |
| `notify`        | 人間待ちを知らせるコマンド (`command`: コマンドと引数の配列)。シェルを通さずに実行します。省略すると知らせません                                 |

書いた節がロードマップに無いとき、承認とみなす節と完了とみなす節が重なるとき、知らない項目があるときは、書き誤りとしてエラーにします。

ロードマップと作業計画書は `wikino` コマンドで読み、下書きがあれば下書きを読みます。
korylusfactory自身の読み取りには、`wikino auth login <スペース>` でログインするトークンに読み取りの権限があれば足ります。
`start` が起動するセッションは、計画書や作業報告書の下書きを読み書きします。
`start` を使うときは、セッションから使う `wikino` に、作業するスペースごとに、下書きの権限 (`draft_page:*`) とページ・トピックの読み取り権限 (`page:read`・`topic:read`) を持つトークンでログインしておきます。
人間キューも、同じ権限で読み書きします。
ページを公開する権限 (`page:write`) は持たせません。
公開は人間がWeb画面で行い、項目の公開を回答の確定に使うためです。

### `start`

`start` は、止めるまで動き続けます。
進めるのは、進行中の作業計画書があればそれ、無ければロードマップの並び (「[`status`](#status)」) の先頭の作業計画書です。
並びの先頭を読み取れないときは、飛ばさずに、人間が作業計画書かロードマップを直すのを待ちます (人間キューを使う設定では、知らせの項目を積みます)。
進める作業計画書が無いときは、ロードマップに現れるのを待ちます。
ロードマップは5分ごとに読み直します。

ブランチを作るタスクは、korylusflowの「[1タスクの流れ](#1タスクの流れ)」と同じ流れで進めます。
タスクのブランチを作る元も、korylusflowの「[ベースブランチ](#ベースブランチ)」と同じ順で決めます。
作業者のセッションはClaude Codeで、レビュアーのセッションは1回目をCodex、2回目以降を前回と別のエージェントで起動します。
セッションには、実行するスキルと引数を指示し、結果を決めた形のJSONで受け取ります。
korylusfactoryは、結果とリポジトリの状態 (タスクのブランチ・コミット・未コミットの変更・レビュードキュメント) に加えて、作業計画書で変わったのがタスクのチェックボックスと実装判断ログだけであることを確かめてから、ステップの完了を記録します。
ブランチを作らない実装者のタスクでは、セッションが作業計画書のタスクにチェックを付けます。
korylusfactoryが完了の条件を確かめてから、次のタスクへ進みます。
計画書の最後まで進むと作業者が作業報告書を書き、処理の流れを書いたときはレビュアーが作業報告書をレビューします。

進み具合は標準出力に、エラーと警告は標準エラーに書きます。
起動したときと作業計画書を始める前には、korylusfactoryが古ければ警告します (「[古いときの警告](#古いときの警告)」)。
同じプロジェクトで `start` を二重には起動できません。

### セッション

セッションは確認なしで動かすため、VMなどの隔離した環境で使います。
pushとPRの作成・マージは、指示で禁じるのに加えて、次で止めます。

- Claude Codeの拒否ルール (`git push`・`gh pr create`・`gh pr merge`)。人間の回答で再開する `korylusfactory resume`・`korylusfactory queue answer` も拒否します
- セッションの `PATH` の先頭に置くGitの入口。`git -C <dir> push` を含めて、pushを拒否する
- pushの宛先を存在しないリモートヘルパーに書き換える補助のgit設定と、無効な `GH_TOKEN`

セッションの時間の上限は2時間です。
セッションが結果を返さずに終わったとき、時間の上限を過ぎたとき、完了の条件を満たさなかったときは、満たせなかった条件を指示に添えて、5分空けて同じステップをやり直します。
3回やり直しても終えられなければ、人間を待ちます。

セッションの指示・結果の形・標準出力・標準エラーは、セッションごとに `docs/private/factory/plans/<計画書名>/sessions/` の下へ残します。

### 止めるとき

`start` は、Ctrl-Cなどのシグナルで止めます。
実行中のセッションは、セッションが起動した子プロセスまで終わらせます。
状態はセッションの結果を記録する前のまま残り、次に起動すると、中断したことを指示に添えて同じステップをやり直します。
止めたセッションを終わらせ切るまでは、次の `start` を起動できません。

### 人間待ちと `resume`

人間の判断が要る場面では、その作業計画書を止めて理由を表示し、人間待ちが解かれるのを状態ファイルで待ちます (5秒ごと)。
人間キューを使う設定では、どの場面も、人間キューの項目に回答を書いて公開すると再開します (「[人間キュー](#人間キュー)」)。
`resume` は、Wikinoに読み書きできないときなどに、端末で再開するコマンドです。

| 場面                                  | 人間が行うこと                                                     | 再開                                     |
| ------------------------------------- | ------------------------------------------------------------------ | ---------------------------------------- |
| 人が行うタスク                        | 作業して、作業計画書のタスクにチェックを付ける                     | `resume`                                 |
| タスクの準備                          | 未コミットの変更を片付けるか、タスクの接頭辞・ベースブランチを直す | `resume`                                 |
| レビューの要人間判断の指摘            | レビュードキュメントの対応方針に回答する                           | `resume`                                 |
| レビューの上限                        | 続けるか打ち切るかを決める                                         | `resume` (続けるときは `--review-limit`) |
| やり直しの上限                        | 止まった原因を取り除く                                             | `resume`                                 |
| セッションからの質問                  | セッションが結果に書いた質問に対応する                             | `resume`                                 |
| 作業報告書の確認 (フィードバックあり) | 作業計画書にフィードバック対応のフェーズを足す                     | `resume`                                 |
| 作業報告書の確認 (完了)               | PRを作ってマージし、ロードマップで項目を完了とみなす節へ移す       | 不要 (「[完了の伝え方](#完了の伝え方)」) |

`resume` は、人間を待っている作業計画書を、待っていた場面に応じて再開します。

- 人が行うタスクとタスクの準備は、作業計画書の最初の未完了のタスクから選び直す
- レビューの待ちは、人間の回答を読んで対応方針に回答し直す。レビューの上限で待っているときは、`--review-limit <回数>` で上限を延ばすと修正のあとに再レビューし、延ばさなければ修正のあと再レビューせずに次へ進む
- やり直しの上限とセッションからの質問は、同じステップを新しいセッションでやり直す
- 作業報告書の確認は、作業計画書にフィードバック対応のフェーズを足しただけであることを確かめてから、そのタスクから進める

再開の条件を満たさないときは、理由を表示して状態を変えません。
人間を待っている作業計画書が無いときと、複数あるときはエラーにします。

### 人間キュー

人間キューの項目は、設定ファイルの `queue` のトピックの1ページです。
人間待ちになると、`start` が項目を新しいページの下書きとして積みます。
項目には、作業計画書・場面・理由と、場面に応じた回答の欄を書きます。

| Wikinoでの状態           | 意味                |
| ------------------------ | ------------------- |
| 新しいページの下書き     | 人間待ち            |
| 公開済みで、下書きが無い | 回答済み            |
| 公開済みで、下書きがある | 差し戻し (人間待ち) |

人間待ちの項目は、Wikinoの下書きの一覧に並びます。
タイトルは `<プロジェクト名> - <計画書名> - <場面> - <積んだ日時>` の形です。
日時は、`start` を実行している環境のタイムゾーン (環境変数 `TZ` か、システムの設定) で書きます。

項目には、スマートフォンのWeb画面でも回答できます。

1. Wikinoの下書きの一覧から項目を開く
2. 「## 回答」の節に回答を書く。選択の欄は選択肢の1つにチェックを付け、自由記述の欄は見出しの下に文を書く
3. ページを公開する

`start` は、人間を待っている間、1分ごとに項目を読みます。
公開されていれば、回答を場面に応じて適用して再開します。

| 場面                                                           | 回答の欄                                                                           |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| レビューの要人間判断の指摘                                     | 指摘ごとの対応方針の選択肢。選んだ選択肢をレビュードキュメントに書いて、修正へ進む |
| レビューの上限                                                 | 「上限を延ばして再レビューする」(上限を1回延ばす) と「打ち切って次へ進む」         |
| セッションからの質問                                           | 自由記述。回答を、同じステップをやり直すセッションの指示に添える                   |
| 人が行うタスク・タスクの準備・やり直しの上限・作業報告書の確認 | 無し。対応してから公開すると、`resume` と同じ条件で再開する                        |
| 並びの先頭を読み取れない・ブランチが取り込まれていない         | 無し。公開は要らず、原因が解けると `start` が項目を片付ける                        |

レビューの指摘で、選択肢に無い対応 (「その他」) は項目では選べません。
人間が、レビュードキュメントの該当する指摘の「対応方針」で「その他」にチェックを付けます。
同じ指摘の「回答」欄に対応を書いてから、端末で `resume` を実行します。

回答の形が誤っているとき (選択肢を選んでいない・2つ選んでいる・選択肢を書き換えたなど) と、再開の条件を満たさないときは、公開されたページに下書きを作り直し、本文の先頭の「差し戻し」の節に理由を書きます。
下書きを直して、もう一度公開します。

項目が公開される前に待ちが解けたとき (`resume` や完了の検知) は、`start` が本文を状態の置き場へ残してから、項目の下書きを削除します。
人間が項目の下書きを削除したときは、積み直します。
Wikinoに読み書きできないときは警告を出し、1分空けてやり直します。
人間待ちの記録と進行中のタスクは止めません。

### 人間待ちの知らせ

人間待ちは、通知のコマンドと、端末への表示で知らせます。

通知のコマンド (設定ファイルの `notify`) は、人間待ちになったとき (項目を積んだあと) と、差し戻したときに1回ずつ実行します。
項目を積めなかったときはURLを渡さずに知らせ、積めたらURLを渡してもう一度知らせます。
並びの先頭を読み取れないことと、ブランチが取り込まれていないことの知らせの項目は、項目を積めたときだけ、URLを渡して知らせます。
人間キューを使わない設定では、この2つの場面は知らせません。
コマンドには次の環境変数だけを渡し、項目の本文は渡しません。

| 環境変数                 | 内容                                                                                                             |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| `KORYLUSFACTORY_PROJECT` | プロジェクト名                                                                                                   |
| `KORYLUSFACTORY_PLAN`    | 計画書名。並びの先頭を読み取れないことの知らせでは、計画書名が分からないため、ロードマップのWikiリンクのタイトル |
| `KORYLUSFACTORY_SCENE`   | 場面。差し戻したときは「<場面> (差し戻し)」                                                                      |
| `KORYLUSFACTORY_URL`     | 項目を編集画面で開くURL。項目を積めていないときは渡しません                                                      |

通知先 (スマートフォンへのプッシュなど) へ送る処理は、コマンドの側に用意します。
通知先の秘密情報は、設定ファイルではなくコマンドの側で持ちます。
次は、ntfyへ送るスクリプトを通知のコマンドにする例です。

```sh
#!/bin/sh
# ~/.local/bin/notify-factory (通知のトピックは、環境変数 NTFY_TOPIC で渡す)
curl -fsS -H "Title: $KORYLUSFACTORY_PROJECT: $KORYLUSFACTORY_SCENE" \
  -H "Click: ${KORYLUSFACTORY_URL:-}" \
  --data-raw "$KORYLUSFACTORY_PLAN" "https://ntfy.sh/$NTFY_TOPIC"
```

```json
{ "notify": { "command": ["notify-factory"] } }
```

コマンドは30秒で終わらせ、失敗と時間切れは警告を出すだけにします。

`start` の標準エラーが端末のときは、端末のタイトルに今の状態を出し、人間待ちになったときにベルを1回鳴らします。
タイトルは、セッション中は `korylusfactory - <計画書名> - タスク 1-2 の実装`、人間待ちでは `korylusfactory - 人間待ち - <場面>` の形です。

### `queue`

`queue` は、人間キューの項目を一覧・表示し、回答を項目の下書きに書きます。
Wikinoを読み書きするだけで、状態ファイルは書きません。
どのプロジェクトからでも、置き場の全プロジェクトの項目を読めます。

| サブコマンド                          | 役割                                                                                                   |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `queue list [--all]`                  | 人間待ちの項目を、積んだ順に表示します。既定はこのプロジェクトの項目で、`--all` で全プロジェクトの項目 |
| `queue show <ページ番号>`             | 項目の本文と、回答の欄 (選択の欄のラベルと選択肢) を表示します                                         |
| `queue answer <ページ番号> <回答>...` | 欄の順に並べた回答を、項目の下書きに書きます。公開はしません                                           |

`queue answer` には、選択の欄にはラベル (`A` など) を、自由記述の欄には回答の文を、欄の順に並べて渡します。
`-` で始まる文は、`--` のあとに渡します。
回答の形を確かめてから書き、回答の欄の前に「回答の書き手: <書き手> (<日時>)」の行を記します。
書き手は、Claude CodeやCodexのセッションの中から実行したかで見分けます。
回答の欄の無い項目には書きません。
回答は、人間がWeb画面で公開して確定します。

どれも `--json` を付けると、JSONで出します。

### 完了の伝え方

作業計画書の完了 (マージ済み) は、コマンドではなく、ロードマップから知ります。
作業報告書の確認を待つ間、`start` はロードマップを5分ごとに読み、次の2つを満たしたら完了を記録して次の作業計画書へ進みます。

1. 作業計画書へのWikiリンクが、完了とみなす節の項目にある
2. タスクでブランチを作ったリポジトリごとに、最後のタスクのブランチが、リモート `origin` の既定のベース (develop、無ければmain) に取り込まれている

1を満たして2を満たさないときは、取り込まれていないブランチを表示して待ちます。
ブランチを作るタスクが無い作業計画書は、1だけで完了とします。
完了を記録した作業計画書は、ロードマップの承認とみなす節にあっても進めません。

### `status`

korylusfactoryのバージョンと、これから進める作業計画書の並びと、進行中の作業計画書を表示します。

並びは、承認とみなす節の項目にある、タイトルが「作業計画書」で終わるWikiリンクを、節の順に、節の中では上から順に並べたものです。
名前だけの項目 (まだ作っていない計画書)・チケットへのリンク・入れ子の項目は読み飛ばします。
同じ作業計画書へのリンクが複数あれば、最初のものだけを残します。
完了を記録した作業計画書は、並びに入れません。

作業計画書ごとに、次のいずれかを表示します。

| 表示                               | 意味                                                              |
| ---------------------------------- | ----------------------------------------------------------------- |
| 計画書名とURL                      | 作業計画書を読み取れた                                            |
| 作業計画書のページが見つかりません | リンクのタイトルの下書きもページも無い                            |
| 作業計画書として読み取れません     | ページはあるが、作業計画書として読み取れない。URLと理由を添えます |

進行中の作業計画書には、現在のステップと人間を待っている理由を添えます。
人間キューに項目を積んでいれば、項目のURLも添えます。
作業報告書の確認を待っているときは、完了を確かめて、取り込まれていないブランチを添えます。

`--json` を付けると、同じ内容をJSONで出します。
ロードマップを読めないとき (未ログイン・Wikinoが止まっているなど) は、理由を標準エラーに表示して終了コード1で終わります。

### 古いときの警告

`status` と `start` は、ビルド元のリポジトリの `main` で、Rustのコード (`crates/`・`Cargo.toml`・`Cargo.lock`) を最後に変えたコミットを調べます。
インストールされているkorylusfactoryがそのコミットを含んでいなければ、`make install-korylusfactory` で入れ直すよう警告します。
警告するだけで、自動では入れ直しません。

比べる前にリモートの `main` を取得し、取得できないときは手元の `main` と比べます。
ビルド元のリポジトリが無いなど確かめられないときは、警告せず、確かめられなかったことと理由を表示します。

### 状態の置き場所

状態は、プロジェクトのルートの `docs/private/factory/` に置きます。

| ファイル                      | 内容                                                                                                                                           |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `config.json`                 | 設定ファイル                                                                                                                                   |
| `plans/<計画書名>/state.json` | 作業計画書ごとの進行 (現在のタスクとステップ・やり直しの回数・人間を待っている理由・完了した時刻・積んだ人間キューの項目) と、タスクごとの記録 |
| `plans/<計画書名>/queue/`     | 公開されずに片付けた項目の本文 (`<ページ番号>.md`)                                                                                             |
| `queue.json`                  | 状態ファイルに持たない待ち (並びの先頭を読み取れない・ブランチが取り込まれていない) に積んだ知らせの項目の記録                                 |
| `queue/`                      | 片付けた知らせの項目の本文 (`<ページ番号>.md`)                                                                                                 |
| `plans/<計画書名>/sessions/`  | セッションごとの記録                                                                                                                           |
| `plans/<計画書名>/state.lock` | ファイルロック用の空のファイル                                                                                                                 |
| `start.lock`・`session.lock`  | `start` の二重起動と、止めたセッションの後始末を見分けるファイルロック用の空のファイル                                                         |

タスクごとの記録は、作業報告書のスキルが材料として読めるよう、korylusflowの `flow.json` の `tasks` と同じ項目名にしています。

### `--version`

`--version` は、バージョン番号・ビルド元のコミット・ビルドした日と、ビルド元のリポジトリの場所を表示します。
`-V` は、ビルド元のリポジトリの場所を省いて1行で表示します。

### インストール

`make install-korylusfactory` でビルドし、`~/.local/bin/korylusfactory` に置きます (`BINDIR=<ディレクトリ>` で置き場所を変えられます)。
ビルドには、`mise.toml` のRustを使います (`mise install rust`)。
`start` を動かしている間にブランチを切り替えても実行中のコードが変わらないよう、ビルドした実行ファイルを使います。

## 取得・実行

koryluslintのビルドには、Goに加えてCコンパイラ (GCCまたはClang) と`CGO_ENABLED=1`が必要です。
シェル・TypeScriptの構文解析に[Tree-sitterのGoバインディング](https://github.com/tree-sitter/go-tree-sitter)を使っています。

各プロジェクトはバージョンを固定して `koryluslint` を取得します。

- Goプロジェクト: `go.mod` のtoolディレクティブで `github.com/korylus/tools/cmd/koryluslint` を固定し、`go tool koryluslint ...` で実行する
- 非Goプロジェクト: miseの `go:` バックエンドで固定取得する

## 開発

```sh
make build                   # koryluslintをビルド (bin/koryluslint)
make install-korylusflow     # korylusflowをビルド (~/.local/bin/korylusflow)
make install-korylusfactory  # korylusfactoryをビルド (~/.local/bin/korylusfactory)
make test                    # GoとRustのテストを実行
make vet                     # go vetを実行
make lint                    # golangci-lintとclippyを実行
make fmt                     # gofmt + goimports + rustfmt + Oxfmtでフォーマット
make fmt-check               # フォーマットチェック
```

`test`・`lint`・`fmt-check` は、`-go`・`-rust` を付けると片方だけを実行します (例: `make test-rust`)。
`fmt-check-md` は、Markdownなどのフォーマットだけを確かめます。
